# jarden-ip-visual

按本轮所选资产交付，不为单项设计补做整套商品图。工作台是每次项目对话的必做交付，不是生成完图片才可选附上的页面；聊天同时说明变化、已核验入口和全部待确认事项，不能把问题藏在页面里。

## 每回合工作台硬门槛

1. 已有项目每次对话开头先运行 `<python> <skill>/scripts/workbench.py <项目> --turn`，恢复真实状态、交付和回执；新设计先 `init`，随即运行同一入口。首次没有图片也展示真实目录、规划与空态，不造占位成果。仅维护 Skill 本身不初始化虚假创作项目；已有相关项目可恢复查看。
2. 本回合保存答案、资产范围、反馈、生成结果、审查或选择后，在下一次生图、等待用户或结束回复前再次运行 `--turn`，同步当前 HTML。只问模型、解释流程或闲聊时，已有项目同样恢复并展示；无变化复用有效交付，不为刷新页面新增图片或业务选择。
3. `--turn` 同步、请求服务与打开，返回本次 `foreground.turn_id` 并重置 pending。宿主有可见网页面板时必须复用标签页展示已核验 URL，可用 `--turn --no-open` 避免系统重复开页。实际核对后用 `--record-foreground <证据.json>` 记录匹配的 `turn_id`、`delivery_id`、`foreground=true`、`images_decoded=true` 和 `inspected_by`；系统 `open` 成功只代表已请求打开。后台业务命令只同步 HTML，不弹窗。
4. 结束回复前必须运行 `workbench.py <项目> --check-turn`。本回合开头已核验且项目、源文件和呈现资源均未变化时直接通过，不重复 `--turn`；有变化则重新 `--turn`、前台核验并记录证据，再检查。不得复用上一回合的 `turn_id`。
5. 同步或展示失败时保留真实产物，明确说明阻塞和恢复入口，不继续生图或宣称本步交付完成。无法服务时保留静态页并说明新选择「尚未提交」；无可见面板时如实说明前台未验证。聊天确认仍有效，但不使未登记、过期或未通过审查的候选自动可选。

以上是 Agent 的执行门槛；本地脚本不能拦截宿主原生图片工具，不能声称程序已替 Agent 强制执行。入口、前台验收与静态回退见 [HTML 交付](references/html-delivery.md)。

## 先路由任务

| 用户意图 | 入口 | 停止点 |
| --- | --- | --- |
| 新做设计 | 默认资产模式 `init`、保存已知信息、`show.next` | 先确认本轮资产范围，再按必要依赖制作 |
| 继续项目 | `show`、最近交付和 `next` | 当前真实下一步，并在聊天正文说明 |
| 改指定图 | 当前轮或定稿、明确图位 | 新轮对比，并在聊天正文说明确认项 |
| 沿方向补变化 | `new-round --based-on` | 候选 HTML，并在聊天正文说明比较与选择项 |
| 补齐缺图 | 已有回执与缺项 | 补齐后的同一交付 |
| 只改文案或顺序 | `copy.json`、图序 | 更新后的预览 |
| 只评审 | 当前产物与约定 | 评审页面，不改选择，聊天正文给结论 |
| 沿用旧固定流程 | schema 3 项目或 `init --workflow legacy` | 保留旧四类笔记组合与原阶段门槛 |
| 更新、迁移或修复安装 | 更新器或迁移器 | 结果与恢复入口 |

路由不能绕过 `show.next`、阶段条件、用户确认、透明检查或独立审查。这里只负责设计视觉和发布素材，不自动发布、不替用户做版权或平台合规判断。

页面是查看与证据载体，不是唯一沟通入口。任何停止点都要在聊天正文写清下一步、全部待确认选项和回复方式；用户是否点击页面按钮，不影响 Agent 主动说明。

## 工作台链接与反馈

- 分享可点击链接前，必须启动受控服务并用真实带 token 的 `/api/state` 健康检查确认。只有 `server.status=ready` 且 `link_check.status=ok` 才能展示 `url`；不得只凭 PID、`server.json`、系统 `open` 返回或页面文件存在判断可访问。
- 启动的页面服务必须能脱离当前命令会话存活。命令结束后可能被回收时，改用持续运行的前台终端会话；仍无法保证存活时只给 `file://` 静态页，并明确「尚未提交」。用户反馈打不开时，先重验并给新入口，不重复旧链接。
- 工作台可以看图、比较和可选提交，但不是必需反馈入口。每次展示页面时，聊天正文必须包含：本轮产物或变化摘要、已验证入口、全部待确认问题或选项、下一步如何回复。不能只给链接、写「去页面里选」，或等用户操作页面后再说明待确认事项。

## 开始或恢复

先执行本地状态、事务和版本检查。普通创作的联网版本查询放在首图交付后或用户明确维护时；离线或关闭检查时跳过。继续使用已有缓存与失败冷却，不新增常驻更新服务。

1. 新项目运行 `init <项目> --input <图> --kind <类型>`，文字想法用 `--kind text`；随后按工作台硬门槛运行 `workbench.py <项目> --turn`，已有项目直接从该入口恢复。核对 `project.py show <项目>` 与返回的 `next` 后继续；类型见 [项目状态](references/project-state.md)。
2. 首次建立身份时看完整输入，区分身份与灵感。恢复时先看当前约定、实际交付、目标完整图和基线；身份不明或参考变化再补看相关输入。不要继承水印、界面、品牌或偶然文字。
3. 用户已经说过的答案立即保存；同一会话可用 `init --reuse-from`。当前明确要求优先于旧偏好；产品形态、尺度和发布方式只在所选资产确实需要时补齐。
4. schema 4 承载资产模式，新 `init` 默认采用；schema 3 的 legacy 项目继续原路径，不自动追加资产语义。schema 1/2 写入前须显式迁移；schema 3 转资产模式也须预览并显式迁移到 4。按 [项目状态](references/project-state.md) 保留未知字段、原图、来源、审查和回执，不补造通过。
5. 核心状态和 HTML 只需 Python 3.10+；图片检查、盲审准备、去底、拼版和发帖整理需要 Pillow。`<python>` 在 macOS/Linux 用 `python3`，Windows 用 `py -3`。

## 先选资产，再补必要信息

首次生成前读 [按需资产工作流](references/asset-workflow.md)，从统一目录提供四组 21 项编号及支持边界。用户已点名的产物直接登记并回显；一个设计请求内沿用范围，追加只展示差量。所选资产合格即可结束，未选宣发不强制场景、九宫格或文案。

探索先比较方向，不精修落选方案；正式采用只精修所选范围并通过适用审查。方向意向不等于批准，不能充当下游前置。角色母版先记录已有身份、主色、保持项和来源；选到结构、三视图、规范或产品资料时才补对应细节。过程图保留真实生成和修改来源，不把补绘效果图称为历史手稿或工厂过程。

目录存在不等于能力全部实现。06 真实可编辑光影分层仍待支持；13—15 只作有来源的设计参考，不是制造文件。未支持目标可登记，但须明确阻塞、降级或交接，不能暗算完成。默认图片能力与授权边界不因资产模式改变，不承诺固定分钟数或未经测量的提速。

## 旧商品流程的信息确认

本节仅适用于 legacy 或所选资产涉及商品与发布的部分。纯线稿、平涂、设定文档不以产品问卷为前置。

按 `show.next` 只补当前影响结果的缺项。用户一句话给出品类、用途、尺度和保持项时一次保存，不拆成重复问卷；用户不用填写内部机位参数。用途和尺度使用自由输入，选项仅作辅助；只有会改变身份、结构或大范围结果的冲突才追问。

一次只推进一个待决定问题，但本轮所有需要用户知道的反馈项、选项和页面入口仍须在聊天正文完整写出；页面不得替代这段说明。

| 次序 | 确认内容 | 已知信息 |
| --- | --- | --- |
| 1 | 产品形态：毛绒、手办、拼图或其他 | 写 `answers.product_form`；其他品类另写 `brief.product_detail` |
| 2 | 图中哪些主体要做 | 一个主体记 `single`；多个逐个列出并加「全部」，道具不自动算主体 |
| 3 | 角色数量及主要用途 | 数量与每轮方向数分开；自由说明摆放、包挂、可拆双用途等，不自动加五金 |
| 4 | 当前产品的设计尺度 | 数值、范围或可观察的定性目标，注明本体/含配件口径和来源；未知可做概念，相关场景前补齐 |
| 5 | 笔记类型和交付方式 | 场景规划前再补未知项；九宫格正好九张，满额追加先处理容量冲突 |

四类：

- **同系列合集**：全家福、逐只展示和生活场景，适合系列出道、测款。
- **IP 设计手稿**：成品首图、三视图、手稿过程、世界观与延展，适合设计师作品展示。
- **单个玩偶多维展示**：一个主角的认脸、尺度、材质、角度和用法，适合单款上新。
- **多个玩偶多场景展示**：一组角色从合照到居家、主题和出门，突出关系与集齐欲。

非毛绒把「玩偶」替换成「产品」但保留图位功能。信息矛盾时只追问当前会影响结果的一项，其他答案保留。

## 选定图片能力

默认使用宿主原生/系统 `imagegen`，选择写入 `image_backend.kind`。不可用则保存待生成状态，不因路径、重试或质量问题自动切换供应商、订阅转接或 API；用户明确选择外部服务时才读 [图片后端](references/image-backends.md)。

原生能力不需要向用户索取 Key。调用前按 [产品与镜头约定](references/product-and-shots.md) 登记生成任务，只有 `should_call=true` 才调用；完成记录真实输出，未决标 `unknown`，不盲目重发。工具没有真实图片不算成功。已授权的可选 API 继续复用原安全凭据入口，Key 不进上下文。

用户明确要求本范围生图即为范围授权，保存其原话与范围；覆盖内不重复询问。补图按钮只登记意向，不能扩大授权。新供应商、新费用边界或超出原范围先说明并取得明确选择；`--authorized` 是记录该依据，不是自行创造授权。

无法生图时保存方向、完整提示词和缺图原因：资产模式保留 `assets new` 的待生成实例，不用空文件执行 `assets record`；legacy 可用 `record-round --allow-missing`。随后按工作台硬门槛同步缺项页面；只能说停在生图，不能把占位、代码绘图或旧图当作新图，也不能批准或推进。

## 每轮制作

1. 本阶段首次或规则变化时读 [阶段规则](references/stages.md) 和 [提示词与视觉验收](references/prompting.md)，选发布组合才读对应笔记类型，未变不重复加载。资产探索通常先比较两方向，明确方向或局部修改先一张；用户指定数量与预算优先，旧项目保留已存设置。
2. 资产模式用 `assets new` 保存所选资产、完整提示词、来源与授权；legacy 用 `new-round` 建轮并填 `round.json` 的 `title`、`idea`、完整 `prompt` 和 `refs`。都须带身份、产品、风格和本轮基线；候选在轮廓、材质或场景策略上实质不同，每项单独出图。资产命令见 [按需资产工作流](references/asset-workflow.md#操作示例)。
3. 保存真实新图并目视检查。场景按 [产品与镜头约定](references/product-and-shots.md) 做 G0 计划检查、独立 G1 合同实际图验收，再由另一位审查者按 [零上下文物理审查](references/physics-review.md) 做 G2；按批组织、逐图给证据，缺审、不确定或失败只修对应项。
4. 资产模式用 `assets record` 登记真实文件及来源，必要审查合格且用户明确采用后才 `assets approve`；legacy 用 `record-round` 登记，再按确认执行 `select`。命令失败必须处理或保存阻塞，不能口头声称已登记。
5. 每个用户可见状态点按工作台硬门槛运行 `workbench.py <项目> --turn`，由它复用或生成不可变交付、更新 HTML，再由宿主前台展示。HTML 同时展示本轮、真实上次交付、比较基线、已知约定、变化和选择；聊天同步给出入口和全部待确认事项，不只返回裸路径。
6. 真实选择回执 `committed=true` 已执行选择，读回当前 `next`，不重复提交；静态草稿或聊天选择才按对应工作流提交一次。提交后再次同步展示，不能用旧页面进入下一步；补图/重做意向不是生图授权，也不能自动代用户选择。

## 商品场景与多角色

以下固定顺序用于 legacy；资产模式仅在所选交付的必要依赖包含商品场景时读取，不给平面或文档资产强加材质、去底或场景前置。

顺序是概念 → 材质方向 → 完整 2D 透明图 → 场景 → 发帖整理。已有明确认可的真实概念、材质、合格透明图或已审场景基准可 `accept-input`，不重复制作；前置条件不能省。直接采用透明主资产须真 alpha、当前独立 identity 通过及真实认可依据；场景基准仍需 G1/G2。

概念数量是角色或设计数，方向数是同一角色本轮备选。多角色先定第一只的头身比、五官和工艺语言，其余逐只生成并确认；后续角色带第一只定稿作风格参考，同时保留各自身份。

透明图是完整正面全身 PNG，不是三维模型。先真实生图并 `check_images.py --alpha`；不支持真透明时用反差纯色底生成，再 `remove_bg.py` 检查毛尖、孔洞和浅深底边缘。通过后才开场景。

场景前按 [产品与镜头约定](references/product-and-shots.md) 保存用途、设计尺度、所需视面和逐图计划；方位、俯仰、产品姿态与取景分开。用户要求增加角度时用 `scene-patch --file`，补丁内写 `op: append`，保留原正面；只改指定图位，不把整组统一改成 45°。

正面主资产保留，只补镜头需要的侧背资料；未知隐藏面先提案确认，来源不因确认而改成用户原稿。多视预览是离散二维效果图，非真实可旋转 3D。尺度用可靠参照和布局核对，手掌不证明厘米。物理关系仍逐图独立盲审，不用 caption 解释错误。

## 回改与停止

每轮先把用户原话保存成：可观察改法、保持项、影响主体或图位、比较基线。直接写明目标时执行；两种理解会改变身份或大范围结构时，只问当前冲突，用 `project.py feedback` 留档。模糊的「不够高级」先定位材质反光、缝线、配色或构图，不得自动换角色或撤销全部确认。

用户硬要求与 Agent 构图建议分开保存。不要自行把画高百分比、留白或道具位置硬化成额外必答/返修条件；按产品镜头的来源政策明确标注建议。用户尺寸、身份、必要视角和交付规格仍必需，实际画出的尺具与物理关系仍须可信，旧无来源约束不自动降级或抹掉负评。

对比保留原图和同图位、同主体、可比较尺寸；局部裁切只作辅助。未受影响图位继续使用有效字节，不重做、不重新收费。相同意见多轮无改善或反馈冲突时停止消耗预算，展示方向判断和两个小范围建议。

## 审查与交付门槛

资产模式按实际内容分级验收：探索保留文件、来源、授权、防重和身份硬要求；正式采用补齐所选资产合同。纯二维内容不强制商品物理检查，涉及真实产品接触、承重、悬挂或尺度声称时仍须适用的 G1/G2。按单项资格推进，失败候选及负评保留，不能拖着落选项继续精修。分级边界见 [按需资产工作流](references/asset-workflow.md)。

G1 对当前合同范围检查实际身份、尺度与镜头覆盖，G2 只检查可见物理，两者执行者与上下文分开；不能把合同、Bible 或 G1 判词塞进物理匿名包。均只接受适用的 `pass`，不确定不是通过。其他类别按 [审查路由](references/review-routing.md) 按需检查，不扩成每张七人审。

发帖前按 [文案规范](references/copywriting.md) 写 `copy.json`。正文对应已生成图片；尺寸、价格、授权、打样和发售时间只写有依据的信息。tag 按类型顺序排列，不抄参考帖品牌、活动和作者名。

默认交付干净图片：不自动添加「AI 效果图、非实拍、仅供尺度示意」等提示条。真实性说明放文案、HTML、manifest 和平台声明；只有用户明确要求才用 `compose.py` 或 overlays 写字，并设 `image_text=user-approved`。拼版或派生标 `method` 和 `sources`，不冒称新生图。

资产按类型交付，文档、素材库和非发布图片不统一强制 3:4。只有选择四种旧发布组合时才进入发帖整理：范围已授权直接 `package_post.py --prepare-review`，仅诊断用 `--dry-run`。按实际输出映射对完整排列做 G1、对新像素做 G2，再正式打包；同一批已审字节可复用，改裁切/字体/源图仍重验。交付 `post/` 编号 3:4 PNG、`caption.md`、`manifest.json` 和预览，旧版保留，再检查规格并呈现。

最终仍在聊天正文给三选一：已完成（推荐）、补新图、重新生成，不只放在页面或文案里。说明这是 AI 设计效果图，发布前由用户核对平台限制和 AI 声明；不替用户发布，也不保证流量、销量或打样效果。

## 更新与迁移

默认只检查版本。用户明确要求更新或修复安装时，按 [更新说明](references/updates.md) 生成计划、校验摘要并显式安装。安装代码不扫描、不迁移项目，不读取图片 Key；项目迁移在单个项目上另行预览和执行。更新失败保留旧版和事务记录。

## 可选延展

本轮已在问选择时不追加问题。用户明确收尾后最多列三项，首项推荐并说清代价；已授权的下一步直接执行。

| 当前交付 | 下一步与代价 |
| --- | --- |
| 一套定稿 | 补真实用法场景：新增一轮生图，可能收费 |
| 发布素材 | 做九宫格：优先复用已有图，缺图才生成 |
| 系列素材 | 延展角色：沿用风格，逐只确认并新增生图 |
